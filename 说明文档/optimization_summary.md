# RL-MACPO 优化总结

## 问题描述
原始MACPO可以运行约43次迭代，而RL-MACPO版本只能运行20-32次迭代。主要原因是额外的评估消耗。

## 基于Agent-Centric方案的优化

### 核心思想
- **极简状态设计**：仅使用冲突强度和历史趋势
- **稀疏通信**：冲突强度>0.5才触发通信
- **单目标奖励**：只优化全局适应度

### 主要优化措施（2024更新）

#### 1. 极简中心差分计算
- 文件：`components/rl_evaluator.cpp`
- 修改：只计算一个代表性维度，使用梯度信息推断其他维度
- 效果：每次中心差分只需2次评估（原来需要4-6次）

#### 2. 稀疏通信机制
- 修改：使用固定阈值0.5触发通信（Agent-Centric方案）
- 最小通信间隔：10轮迭代
- 效果：显著减少通信频率和相关评估消耗

#### 3. 优化缓存策略
- 缓存有效性阈值：从1%降到0.1%
- 冲突评估间隔：从10增加到20
- evaluate函数：每5次调用才重新计算冲突
- 效果：大幅减少重复计算

#### 4. 简化RL组件
- 策略网络输出：[-0.1, 0.1]（与Agent-Centric一致）
- 奖励函数：-log(全局适应度)
- 效果：降低计算复杂度

### 预期效果
- 迭代次数：约40-43次（接近原始MACPO）
- 保留RL自适应能力
- 通信开销显著降低

### 使用建议

1. **监控模式**：
   ```cpp
   // 查看每轮消耗的评估次数
   cout << "Iter " << iter << " (consumed: " << eval_consumed << ")" << endl;
   ```

2. **调试参数**：
   - 如需更多迭代：增加MIN_COMMUNICATION_INTERVAL到15
   - 如需更好收敛：减少CONFLICT_EVAL_INTERVAL到15

3. **性能对比**：
   - 原始MACPO：43次迭代，全通信
   - 优化前RL-MACPO：20-32次迭代
   - 优化后RL-MACPO：40-43次迭代，稀疏通信

## 评估消耗分析

### 原始版本每次迭代的评估消耗：
1. **优化阶段**：`gen_times`次generation
2. **通信阶段**：每个邻居`1 + 3×len`次评估
3. **最终评估**：1次全局评估

### RL-MACPO额外的评估消耗：
1. **冲突计算**：
   - 每次`evaluate`调用都会计算冲突
   - 原本每10次迭代使用中心差分（4次额外评估）
2. **通信决策**：`should_communicate`中的冲突计算
3. **RL更新**：`update_rl_weight`中的冲突计算

## 优化措施

### 1. 完全禁用中心差分计算
- 文件：`components/rl_evaluator.cpp`
- 修改：注释掉所有中心差分代码，只使用简单的欧几里得距离
- 效果：每10次迭代节省4次评估

### 2. 增加冲突评估间隔
- 文件：`components/evaluator.h`
- 修改：`CONFLICT_EVAL_INTERVAL`从5增加到10
- 效果：减少精确冲突计算频率

### 3. 提高通信阈值
- 文件：`components/rl_evaluator.cpp`
- 修改：
  - 通信阈值范围从[0.5,0.7]提高到[0.6,0.8]
  - 最小通信间隔从3增加到5
- 效果：减少通信频率，节省通信阶段的评估

### 4. 添加RL更新开关
- 文件：`MACPO.cpp`
- 修改：添加`use_rl_update`变量控制是否使用RL权重更新
- 效果：可以完全禁用RL功能，恢复到原始版本的行为

## 使用建议

1. **最大化迭代次数**：
   ```cpp
   bool use_rl_update = false;  // 禁用RL更新
   ```

2. **平衡性能和功能**：
   - 保持当前设置（use_rl_update = true）
   - 预期迭代次数：约35-40次

3. **进一步优化**：
   - 增加缓存有效期（减少`var_range * 0.01`到更小值）
   - 减少通信阶段的扰动计算维度
   - 优化粒子群评估策略

## 监控输出
每次迭代会输出：
- 当前评估次数和本轮消耗
- 适应度值、权重、冲突强度
- 是否进行了通信

这些信息有助于进一步调优算法性能。
